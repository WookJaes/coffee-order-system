# ADR-001 포인트 충전은 사용자 행 비관적 락으로 직렬화

## 상태

Accepted. 결정일: 2026-07-14.

## 맥락

포인트 충전은 기존 `points` 행의 잔액을 증가시키거나, 첫 충전이면 새 `points` 행을 생성한다. 같은 사용자의 첫 충전 요청이 동시에 들어오면 `points.user_id` 유니크 제약 위반이 발생할 수 있고, 기존 잔액 충전도 동시 갱신 시 누적 금액과 `CHARGE` 이력이 어긋날 수 있다.

`points` 행은 첫 충전 전에는 존재하지 않으므로 포인트 행 자체를 잠금 기준으로 삼을 수 없다. 반면 충전 대상 사용자 행은 항상 존재한다.

## 결정

포인트 충전 트랜잭션은 `UserRepository.findByIdWithPessimisticLock`으로 사용자 행을 `PESSIMISTIC_WRITE` 잠근다. 잠금 획득 후 포인트 행을 조회하고, 없으면 생성하거나 있으면 잔액을 증가시킨다. 포인트 변경과 `CHARGE` 이력 저장은 같은 트랜잭션으로 처리한다.

## 근거

- 사용자 행은 충전 전에도 존재하므로 첫 충전과 기존 포인트 충전에 같은 직렬화 기준을 제공한다.
- 여러 애플리케이션 인스턴스가 같은 MySQL을 사용해도 DB가 최종 잠금 지점이 된다.
- 포인트 잔액과 충전 이력을 같은 트랜잭션에서 처리해 잔액만 변경되거나 이력만 남는 상황을 막는다.

## 대안 비교

| 선택지 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 사용자 행 DB 비관적 락 | 첫 충전과 기존 충전을 하나의 기준으로 직렬화한다. | 같은 사용자의 충전은 대기한다. | 채택 |
| 포인트 행 DB 비관적 락 | 기존 포인트가 있으면 잔액 기준과 직접 연결된다. | 첫 충전에는 잠글 행이 없어 생성 경합을 막지 못한다. | 제외 |
| Redis 분산 락 | DB 진입 전 경합을 줄일 수 있다. | TTL·락 해제·Redis 장애와 DB 트랜잭션 경계를 추가로 관리해야 한다. | 제외 |

## 결과 (트레이드오프)

같은 사용자의 충전 요청은 직렬화되어 처리 지연이 늘 수 있다. 다만 사용자별 포인트는 정합성이 우선인 데이터이며, 사용자 간 충전은 서로 독립적으로 처리된다.

## 검증 계획

- 포인트가 없는 사용자에게 동시 충전해도 포인트 행이 한 건만 생성되는지 확인한다.
- 같은 사용자 동시 충전 후 잔액이 충전 합계와 일치하는지 확인한다.
- 성공 충전 건수와 `CHARGE` 이력 건수가 일치하는지 확인한다.
