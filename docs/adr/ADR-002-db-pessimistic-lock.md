# ADR-002 주문 포인트 차감에 DB 비관적 락 사용

## 상태

Accepted. 결정일: 2026-07-14.

## 맥락

같은 사용자가 동시에 여러 주문을 요청하면 동일한 포인트 잔액을 기준으로 결제가 진행되어 잔액이 음수가 되거나 포인트 사용 이력이 누락될 수 있다. 현재 포인트 충전은 사용자 행을 `PESSIMISTIC_WRITE`로 잠가 직렬화하는 방식을 사용한다.

주문 결제도 `points`의 사용자별 row를 기준으로 포인트를 차감하고, 주문·포인트 이력·Outbox 이벤트를 하나의 트랜잭션으로 저장해야 한다.

## 결정

주문 결제 트랜잭션에서 `PointRepository.findByUserIdForUpdate`와 같은 사용자별 포인트 조회에 `PESSIMISTIC_WRITE`를 적용한다. 잠금을 얻은 뒤 잔액을 확인하고 차감하며, 주문·사용 이력·Outbox 이벤트를 같은 트랜잭션에서 저장한다.

포인트 row가 없으면 잠금 생성이나 신규 포인트 생성 없이 `POINT_NOT_FOUND`로 실패한다.

## 근거

- 정합성의 기준 데이터인 `points` row를 잠그므로 여러 애플리케이션 인스턴스에서도 DB가 최종 직렬화 지점이 된다.
- 포인트 충전과 주문 결제 모두 DB 비관적 락을 사용하므로 구현과 운영 모델을 일관되게 유지할 수 있다.
- 별도 Redis 인프라·TTL·락 해제 정책 없이 Spring 트랜잭션 롤백과 함께 잠금이 해제된다.

## 대안 비교

| 선택지 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| DB 비관적 락 | DB 잔액과 같은 트랜잭션에서 최종 정합성을 보장한다. | 동일 사용자 요청은 대기하고 DB 경합이 증가할 수 있다. | 채택 |
| Redis 분산 락 | DB 진입 전 경합을 줄일 수 있다. | Redis 장애, TTL, 해제 실패와 DB 트랜잭션 경계를 추가로 관리해야 한다. | 제외 |
| 잠금 없이 조건부 차감 | 구현이 짧을 수 있다. | 이력·주문 저장과의 원자성 및 동시 요청 정책이 불명확해진다. | 제외 |

## 결과 (트레이드오프)

동일 사용자 동시 주문은 직렬화되어 음수 잔액과 중복 차감을 방지한다. 대신 해당 사용자의 주문 처리 지연이 증가할 수 있으므로, 동시 주문 테스트에서 성공 건수·최종 잔액·포인트 사용 이력 건수를 함께 확인한다.

## 검증 계획

- 같은 사용자로 동시에 주문해 잔액이 음수가 되지 않는지 확인한다.
- 성공 주문 수와 `USE` 포인트 이력 수가 일치하는지 확인한다.
- 잔액 부족 요청이 주문·이력·Outbox 데이터를 남기지 않는지 확인한다.
