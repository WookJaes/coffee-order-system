# ADR-006 최근 7일 인기 메뉴는 일자별 Redis ZSET 합산 후 애플리케이션에서 동점 정렬

## 상태

Implemented. 결정일: 2026-07-14, 구현일: 2026-07-15.

## 맥락

Issue #8은 최근 7일 주문 횟수로 인기 메뉴 Top 3를 반환해야 한다. 랭킹 데이터는 일자별 Redis ZSET에 분산되어 있고, 같은 주문 수의 메뉴는 메뉴 ID 오름차순으로 결정해야 한다. Redis ZSET 기본 순서만으로는 숫자 메뉴 ID 오름차순 동점 규칙을 API 계약으로 보장하기 어렵다.

## 결정

조회 시 Asia/Seoul 기준 요청일을 포함한 최근 7개 달력일의 `coffee:ranking:{yyyy-MM-dd}` 키를 합산한다. 일자별 ZSET·`DATA/EMPTY` 상태·처리 주문 건수는 하나의 Redis Lua snapshot으로 읽는다. 합산 결과는 점수 내림차순, 메뉴 ID 숫자 오름차순으로 애플리케이션에서 정렬해 최대 3건만 반환한다.

랭킹에 남은 메뉴 ID는 메뉴 조회로 이름과 판매 정보를 조합한다. 메뉴가 3개 미만이면 존재하는 항목만 반환한다. Redis 데이터가 없거나 유실되거나 일자별 처리 건수가 `orders` 원장의 `PAID` 주문 건수와 다르면 기존 재구성 잠금으로 원장 기준 랭킹·count를 재구성한다.

## 근거

- 날짜별 키를 합산하면 기간 경계에서 만료와 조회가 단순하다.
- 애플리케이션의 숫자 비교로 동점 규칙을 명확하게 고정할 수 있다.
- `orders`를 원본으로 유지하면 Redis가 파생 데이터여도 정확한 복구 경로가 있다.

## 결과 (트레이드오프)

Redis는 조회 최적화용 파생 데이터라 주문 직후 반영에는 Consumer 지연이 있을 수 있다. 복구 집계는 MySQL 부하가 더 크므로 Redis 재구성이나 장애 복구 시에만 수행한다.

일자별 Redis ZSET과 `DATA`/`EMPTY` 상태 키의 날짜는 `OrderPaidEvent`에 포함된 `orders.ordered_at`을 Asia/Seoul 날짜로 변환해 결정한다. 따라서 Consumer 지연, Kafka 재시도, 재소비가 있어도 주문이 속한 달력일과 최근 7일 집계 범위가 바뀌지 않는다.

7일치 ZSET에 멤버가 하나도 없거나 Redis 처리 건수가 원장과 다르면 별도 유실 마커 없이 `PAID` 주문 원장을 조회한다. 원장 결과가 있으면 일자별 ZSET과 count를 기존 TTL로 다시 채우고, 결과도 없으면 모든 날짜에 count `0`과 `EMPTY` 상태를 기록한 뒤 정상적인 무주문 상태로 빈 목록을 반환한다. 인기 메뉴 응답에는 현재 `ACTIVE` 메뉴만 포함하며, 제외된 메뉴는 다음 순위로 보충한다.

각 일자는 `DATA` 또는 `EMPTY` 완료 상태 키와 처리 count 키를 함께 가진다. Consumer는 Lua에서 `DATA` 상태·ZSET·count를 동시에 기록하고, 재구성은 각 날짜의 ZSET·count를 기록한 뒤 그 날짜의 완료 상태를 기록한다. 조회는 `DATA` 상태인데 ZSET이 없거나, `EMPTY` 상태인데 ZSET이 있거나, 상태·count가 없는 날짜가 하나라도 있으면 부분 유실 또는 중단된 재구성으로 보고 DB 원장으로 전체 기간을 복구한다. 따라서 재구성 도중 프로세스가 종료돼도 완료 상태가 없는 기간은 다음 조회에서 다시 복구된다.

재구성은 별도 Redis 잠금 키로 한 번만 실행한다. 잠금을 얻은 요청은 잠금 직후 완료 상태를 다시 확인해 Consumer가 먼저 반영한 완전한 데이터가 있으면 DB 재구성을 건너뛴다. 재구성 중에는 Lua 집계가 재시도 가능한 예외를 반환하고, 재구성은 최근 7일 `PAID` 주문의 Outbox 이벤트 마커도 함께 복원한다. 따라서 잠금 해제 뒤 이미 집계된 이벤트가 다시 Consumer에 도착해도 점수가 중복 증가하지 않는다.

잠금에는 UUID 토큰을 저장한다. `RANKING_REDIS_REBUILD_LOCK_RENEW_INTERVAL`마다 token compare-and-expire Lua를 실행해 같은 토큰일 때만 `RANKING_REDIS_REBUILD_LOCK_TTL`을 연장하며, 연장 실패·Redis 오류·다른 토큰 소유는 즉시 소유권 상실로 처리한다. 재구성은 DB 조회 뒤와 Redis 쓰기 직전에 이를 확인해 이후 점수표를 수정하지 않는다.

실패 정리는 모두 조건부 Lua로 수행한다. 아직 같은 토큰이 잠금을 보유하면 그 요청의 7일 랭킹 ZSET·count·`DATA`/`EMPTY` 상태 키를 삭제한다. 소유권을 잃었다면 공유 ZSET·count·상태 키는 삭제하지 않아 새 소유자의 재구성을 침범하지 않는다. 이번 재구성이 새로 만든 이벤트 마커에는 UUID 토큰을 값으로 저장하고, 그 값이 같은 경우에만 삭제한다. 다음 요청은 완료 상태 불일치를 감지해 DB 원장으로 7일 전체를 다시 복구한다.

재구성의 CLEAR·마커 생성·ZSET 기록·완료 상태 기록은 모두 잠금 키와 UUID 토큰을 함께 받는 Lua로 실행한다. 따라서 토큰 확인 뒤 별도 Redis 명령을 실행하는 경쟁 창이 없다. `PAID` 일자 집계와 Outbox 이벤트 마커 조회는 호출자 트랜잭션을 suspend하는 `REQUIRES_NEW` 읽기 전용 `REPEATABLE_READ` 트랜잭션에서 같은 DB snapshot으로 읽어, 호출자의 isolation과 관계없이 두 조회 사이에 커밋된 주문을 점수 없이 marker만 복원하지 않는다.

조회는 상태와 별도로 Redis count와 DB의 일자별 `PAID` 주문 건수도 비교한다. 하나라도 다르면 Redis가 정상 상태처럼 보여도 DB snapshot 결과를 응답하고 기존 잠금으로 복구를 시도한다. 다른 인스턴스가 이미 잠금을 보유한 경우에도 오래된 Redis 결과를 반환하지 않는다.

## 검증 계획

- 7개 일자 키의 점수가 정확히 합산되는지 확인한다.
- 동점 메뉴가 메뉴 ID 오름차순으로 반환되는지 확인한다.
- 3개 미만 메뉴와 Redis 유실 후 `orders` 기반 재구성 결과를 확인한다.
- 외부 트랜잭션 안에서 재구성을 호출하고 두 DB 조회 사이에 새 주문을 커밋해도 점수와 복원 marker가 같은 snapshot만 사용함을 실제 MySQL로 확인한다.
- `DATA` 뒤 미반영 주문, `EMPTY` 뒤 미반영 주문, Outbox 지연·Kafka DLT, duplicate eventId의 ZSET/count 무증가, Redis snapshot과 Consumer 갱신의 동시성, 여러 서버의 재구성 잠금 경쟁을 확인한다.
