# ADR-006 최근 7일 인기 메뉴는 일자별 Redis ZSET 합산 후 애플리케이션에서 동점 정렬

## 상태

Accepted. 결정일: 2026-07-14.

## 맥락

Issue #8은 최근 7일 주문 횟수로 인기 메뉴 Top 3를 반환해야 한다. 랭킹 데이터는 일자별 Redis ZSET에 분산되어 있고, 같은 주문 수의 메뉴는 메뉴 ID 오름차순으로 결정해야 한다. Redis ZSET 기본 순서만으로는 숫자 메뉴 ID 오름차순 동점 규칙을 API 계약으로 보장하기 어렵다.

## 결정

조회 시 요청일을 포함한 최근 7일의 `coffee:ranking:{yyyy-MM-dd}` 키를 합산한다. 합산 결과는 점수 내림차순, 메뉴 ID 숫자 오름차순으로 애플리케이션에서 정렬해 최대 3건만 반환한다.

랭킹에 남은 메뉴 ID는 메뉴 조회로 이름과 판매 정보를 조합한다. 메뉴가 3개 미만이면 존재하는 항목만 반환한다. Redis 데이터가 없거나 유실되면 `orders`의 최근 7일 `PAID` 주문을 원본으로 집계해 랭킹을 재구성한다.

## 근거

- 날짜별 키를 합산하면 기간 경계에서 만료와 조회가 단순하다.
- 애플리케이션의 숫자 비교로 동점 규칙을 명확하게 고정할 수 있다.
- `orders`를 원본으로 유지하면 Redis가 파생 데이터여도 정확한 복구 경로가 있다.

## 대안 비교

| --- | --- | --- | --- |
| 7일 ZSET 합산 후 애플리케이션 정렬 | 일자 단위 관리와 정확한 동점 규칙을 함께 만족한다. | 합산 결과와 메뉴 정보를 조합해야 한다. | 채택 |
| 단일 누적 ZSET | 조회가 단순하다. | 7일 경과 데이터를 정확히 제거하기 어렵다. | 제외 |
| 매 요청마다 MySQL 집계 | 원본 데이터만 사용한다. | 인기 조회가 늘면 집계 비용이 커진다. | 제외 |

## 결과 (트레이드오프)

Redis는 조회 최적화용 파생 데이터라 주문 직후 반영에는 Consumer 지연이 있을 수 있다. 복구 집계는 MySQL 부하가 더 크므로 Redis 재구성이나 장애 복구 시에만 수행한다.

7일치 ZSET에 멤버가 하나도 없으면 별도 유실 마커 없이 `PAID` 주문 원장을 조회한다. 원장 결과가 있으면 일자별 ZSET을 기존 TTL로 다시 채우고, 결과도 없으면 정상적인 무주문 상태로 빈 목록을 반환한다. 인기 메뉴 응답에는 현재 `ACTIVE` 메뉴만 포함하며, 제외된 메뉴는 다음 순위로 보충한다.

재구성은 별도 Redis 잠금 키로 한 번만 실행한다. 잠금을 얻은 요청은 잠금 직후 일자별 ZSET을 다시 읽어 Consumer가 먼저 반영한 데이터가 있으면 DB 재구성을 건너뛴다. 재구성 중에는 Lua 집계가 재시도 가능한 예외를 반환하고, 재구성은 최근 7일 `PAID` 주문의 Outbox 이벤트 마커도 함께 복원한다. 따라서 잠금 해제 뒤 이미 집계된 이벤트가 다시 Consumer에 도착해도 점수가 중복 증가하지 않는다. 재구성 실패 시 그 요청이 만든 마커와 ZSET 키를 삭제해 다음 요청이 정상적으로 복구할 수 있게 한다. 잠금 TTL은 `RANKING_REDIS_REBUILD_LOCK_TTL`로 일반 랭킹 키 TTL과 분리한다.

## 검증 계획

- 7개 일자 키의 점수가 정확히 합산되는지 확인한다.
- 동점 메뉴가 메뉴 ID 오름차순으로 반환되는지 확인한다.
- 3개 미만 메뉴와 Redis 유실 후 `orders` 기반 재구성 결과를 확인한다.
