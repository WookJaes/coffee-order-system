# ADR-003 주문 완료 이벤트에 Transactional Outbox 사용

## 상태

Accepted. 결정일: 2026-07-14.

## 맥락

주문 완료 이벤트는 이후 Kafka를 통해 데이터 수집과 인기 메뉴 랭킹 갱신에 사용된다. 주문 트랜잭션에서 Kafka를 직접 발행하면 브로커 장애가 주문 실패로 전파될 수 있고, 주문을 저장한 뒤 별도로 발행하면 이벤트가 유실될 수 있다.

현재 스키마의 `order_events`는 주문 ID, 사용자 ID, 메뉴 ID, 결제 금액, 상태, 재시도 횟수를 보관하며 주문당 하나의 이벤트만 허용한다.

## 결정

주문 결제 성공 시 `orders`, `points`, `point_histories`와 함께 `order_events`에 `PENDING` 이벤트를 저장한다. 이 저장은 하나의 DB 트랜잭션으로 처리한다.

이번 범위는 Outbox 저장까지만 포함한다. Kafka Producer, PENDING 이벤트 조회·발행, `SENT`·`FAILED` 상태 전환, 재시도와 Consumer 구현은 후속 범위다.

## 근거

- 주문 원장과 발행 대상 이벤트가 함께 커밋되거나 함께 롤백되어 이벤트 유실 창을 줄인다.
- Kafka 장애가 주문 결제 API의 즉시 실패로 전파되지 않는다.
- `order_events.order_id` 유니크 제약으로 한 주문의 Outbox 이벤트 중복 생성을 DB 수준에서 방지한다.

## 대안 비교

| 선택지 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| Transactional Outbox | 주문 데이터와 이벤트 대상을 같은 트랜잭션으로 저장한다. | 별도 발행·재시도 작업이 필요하다. | 채택 |
| 트랜잭션 내부 Kafka 직접 발행 | 구현 흐름이 짧아 보인다. | 브로커 실패가 주문 성공 여부에 영향을 주고 DB/Kafka 원자성을 보장하지 못한다. | 제외 |
| 주문 저장 후 비동기 발행 | 요청 응답은 빠르게 반환할 수 있다. | 프로세스 장애 시 이벤트가 유실될 수 있다. | 제외 |

## 결과 (트레이드오프)

주문 성공과 Kafka 발행 시점은 분리되므로 랭킹 반영은 즉시 일관성이 아니다. 이벤트 발행기는 `PENDING` 이벤트를 안전하게 재시도해야 하며, Consumer는 at-least-once 전달을 전제로 이벤트 ID 또는 주문 ID 기준 멱등 처리가 필요하다.

## 검증 계획

- 정상 주문 시 `order_events`에 `PENDING` 이벤트가 하나 저장되는지 확인한다.
- 주문 또는 포인트 차감 실패 시 Outbox 이벤트가 저장되지 않는지 확인한다.
- 같은 멱등 요청의 재시도와 동시 요청에서 주문당 Outbox 이벤트가 하나만 생성되는지 확인한다.
